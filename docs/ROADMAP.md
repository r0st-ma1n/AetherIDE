# Roadmap AetherIDE

Единый план разработки. Обновлено: 2026-10-04.

## Цель

**v1 — первый настоящий VST3-плагин из AetherIDE.** Пользователь создаёт проект в IDE,
объявляет параметры, пишет DSP в `processBlock`, жмёт Build и получает `.vst3`, который
загружается в DAW, звучит, автоматизируется и сохраняется вместе с проектом DAW.

В v1 у плагина **нет собственного окна**: DAW показывает свой стандартный интерфейс
параметров. Своё окно с виджетами из дизайнера — это v2 (блок F).

### Не входит в v1

- собственный GUI плагина в DAW (v2);
- MIDI и инструменты, библиотека DSP-примитивов;
- CLAP, AU, macOS и Linux — v1 собирается и проверяется только на Windows x64;
- live preview, hot-reload, Designer 2.0.

## Как пользоваться этим документом

- Документ разбит на **блоки** (A, B, C…), блоки — на **задачи** (A1, A2…),
  задачи — на **подзадачи** (чекбоксы).
- Задача берётся в работу целиком: заводится issue, ветка `feat/<issue>-<short-desc>`
  (см. [GIT_CONVENTIONS.md](./GIT_CONVENTIONS.md)).
- PR, который закрывает подзадачи, **в том же PR отмечает их чекбоксы** здесь.
  Задача считается сделанной, когда выполнены все пункты «Готово, когда».
- Размер: **S** — до дня, **M** — 2–4 дня, **L** — неделя и больше.
- Если план меняется — меняем этот документ в отдельном коммите `docs(roadmap): ...`.

## A. Ядро фреймворка

Сейчас `framework/core` — прототип: буфер сам владеет памятью, параметры — простые `float`
без потокобезопасности, нет состояния и нет точки входа плагина. Цель блока — API, поверх
которого можно написать любой адаптер хоста, и headless-хост для тестов без DAW.

### A1. AudioBuffer без владения памятью · S

Зачем: хост отдаёт готовые указатели на каналы; копировать их в `vector<vector<float>>`
на каждый блок нельзя (аллокации в аудиопотоке).

- [ ] `AudioBuffer` хранит `float* const*` + число каналов и сэмплов, ничего не аллоцирует
- [ ] Отдельный `OwningAudioBuffer` (или helper) для тестов и offline-рендера
- [ ] Раздельные входные и выходные буферы в `ProcessContext` (in-place тоже допустим)
- [ ] Обновить `examples/gain` и тесты

Готово, когда: `processBlock` не делает аллокаций; тесты зелёные.

### A2. Параметры, готовые к хосту · M

Зачем: VST3 работает с нормализованными значениями 0..1 и числовыми `ParamID`;
значение пишет один поток, а читает другой.

- [ ] Значение хранится в `std::atomic<float>`
- [ ] Стабильный числовой ID (хеш строкового id, проверка коллизий при `addFloat`)
- [ ] `toNormalized` / `fromNormalized` с учётом `step` (дискретные параметры)
- [ ] Флаги: `automatable`, `isBypass`; единица измерения (`dB`, `%`, `Hz`)
- [ ] `valueToText` / `textToValue` для отображения в DAW
- [ ] Типы-обёртки: bool (кнопка) и choice (список) поверх float
- [ ] `ParameterLayout`: параметры не переаллоцируются после создания (указатели стабильны)

Готово, когда: юнит-тесты на нормализацию, round-trip текста и уникальность ID.

### A3. Сглаживание параметров · S

Зачем: без сглаживания резкий скачок gain даёт щелчки (бывшая задача D1-T1).

- [ ] `SmoothedValue` (линейное или экспоненциальное, время задаётся в мс)
- [ ] Сброс при `prepareToPlay` с новым sample rate
- [ ] Пример использования в GainPlugin

Готово, когда: тест — скачок значения даёт монотонную рампу нужной длины.

### A4. Состояние плагина · S

Зачем: DAW сохраняет и восстанавливает плагин вместе с проектом и пресетами.

- [ ] `getState()` / `setState()` в `PluginProcessor`: версия формата + пары `id → value`
- [ ] Неизвестные id при загрузке игнорируются, отсутствующие получают default
- [ ] Хук для пользовательских данных (opaque blob)

Готово, когда: тест round-trip; загрузка состояния старой версии не падает.

### A5. Описание плагина и точка входа · M

Зачем: адаптеру хоста нужно знать, что за плагин, и уметь его создать.

- [ ] `PluginInfo`: имя, вендор, версия, URL/e-mail, уникальный ID, категория (Fx/Instrument)
- [ ] Конфигурация шин: mono→mono, stereo→stereo (v1 — без sidechain)
- [ ] `getLatencySamples()`, `getTailSeconds()`, поддержка bypass
- [ ] Макрос `AETHER_PLUGIN(ClassName)` — регистрирует фабрику процессора
- [ ] Документация API в Doxygen-комментариях

Готово, когда: адаптер может получить `PluginInfo` и экземпляр процессора, не зная класса.

### A6. Headless-хост и тесты · M

Зачем: проверять плагин без DAW — и руками, и в CI.

- [ ] Утилита `aether_host`: грузит плагин, рендерит WAV/синус через `processBlock`
- [ ] Заменить `examples/gain/main.cpp` на тест поверх неё
- [ ] Тест реального GainPlugin: gain 0.5 → амплитуда 0.5, без щелчков при смене
- [ ] Закрепить версию CLAP в `FetchContent` (сейчас `GIT_TAG main`) или убрать, пока не нужен

Готово, когда: `ctest` прогоняет тесты ядра и тест GainPlugin.

## B. Параметры в проекте и кодогенерация

Сейчас генератор создаёт только класс `<Name>UI`, а параметры нигде не объявлены —
`getParameter(...)` всегда возвращает `nullptr`. Цель — проект `.aether` описывает
плагин целиком, а генератор создаёт рабочий процессор.

### B1. Параметры и метаданные в `.aether` · M

- [ ] Схема v2: раздел `plugin` (имя, вендор, ID, версия, категория) и `parameters`
      (id, name, type, min, max, default, step, unit)
- [ ] Миграция v1 → v2 при открытии (через существующее версионирование схемы)
- [ ] Валидация AJV: уникальные id, `min < max`, default в диапазоне
- [ ] Тесты на миграцию и валидацию

### B2. Параметры в дизайнере · M

- [ ] Панель «Parameters»: список, добавление, редактирование, удаление
- [ ] У виджета свойство `parameterId` — выбор из списка параметров
- [ ] Удаление параметра, к которому привязаны виджеты, — с предупреждением
- [ ] Undo/Redo для всех операций (Command Pattern)

### B3. Генерация процессора · L

- [ ] Новые шаблоны `<Name>Processor.h/.cpp`: наследник `PluginProcessor`,
      `createParameters()` из `.aether`, `AETHER_PLUGIN(...)`
- [ ] `processBlock`, `prepareToPlay`, `releaseResources` — внутри `USER CODE`-регионов
- [ ] Генерация `PluginInfo` из раздела `plugin`
- [ ] Привязка виджетов в `setupUI` — по `parameterId`, а не по id виджета
- [ ] Round-trip: пользовательский код сохраняется при перегенерации
- [ ] Fixture-тесты генератора

### B4. Шаблон проекта и sample · S

- [ ] New Project wizard спрашивает имя плагина, вендора и создаёт параметр по умолчанию
- [ ] `samples/GainPlugin` пересоздан новым генератором, в нём настоящий gain с A3
- [ ] Сгенерированный проект собирается и проходит тест из A6

Готово (блок B), когда: новый проект из wizard собирается и в headless-хосте меняет звук.

## C. VST3-адаптер

Пишем адаптер напрямую на VST3 SDK, без промежуточного CLAP. Код — в `framework/vst3/`.

### C1. Подключение VST3 SDK · S

- [ ] `FetchContent` с закреплённым тегом SDK; отключить сборку примеров и hosting
- [ ] Перепроверить лицензию SDK для проприетарного проекта, записать вывод в `docs/`
- [ ] Опция CMake `AETHER_BUILD_VST3` (по умолчанию ON)

### C2. Обработка звука и параметры · L

- [ ] Класс на базе `SingleComponentEffect`, создаёт процессор через фабрику из A5
- [ ] `setupProcessing` / `setActive` → `prepareToPlay` / `releaseResources`
- [ ] `process`: передача буферов через A1 без копирования
- [ ] Изменения параметров из `IParameterChanges` (v1: последнее значение в блоке + сглаживание A3)
- [ ] Регистрация параметров у контроллера: имя, единицы, шаги, флаги, текст из A2
- [ ] Bypass, latency, tail
- [ ] Поддержка 32-bit float; 64-bit — отказ через `canProcessSampleSize`

### C3. Состояние и шины · M

- [ ] `getState` / `setState` через A4
- [ ] `setBusArrangements`: mono и stereo, остальное — отказ
- [ ] Синхронизация контроллера после `setState` (DAW показывает правильные значения)

### C4. CMake-функция и бандл · M

- [ ] `aether_add_plugin(<target> FORMATS VST3)` — один вызов в CMakeLists проекта
- [ ] Бандл `<Name>.vst3/Contents/x86_64-win/<Name>.vst3` + `moduleinfo.json`
- [ ] Уникальные FUID из `PluginInfo` (детерминированно из ID плагина)
- [ ] Переключить шаблон `CMakeLists.txt.template` и `samples/GainPlugin` на функцию

### C5. Валидатор в тестах · S

- [ ] Собрать `validator` из SDK
- [ ] CTest-тест: `validator` на собранном GainPlugin.vst3

Готово (блок C), когда: GainPlugin.vst3 проходит validator без ошибок.

## F. v2: собственное окно плагина

Детализируется после выпуска v1. Крупные задачи:

- **F1. Рендерер** — offscreen/software рендер (бывшая G2-T2), затем GPU при необходимости
- **F2. Отрисовка и ввод виджетов** — Knob/Slider/Button рисуются и реагируют на мышь
- **F3. Окно в DAW** — `IPlugView` на Win32 HWND, ресайз, HiDPI
- **F4. Связь UI ↔ хост** — виджеты меняют параметры через контроллер, автоматизация
  двигает виджеты (бывшая G2-T3)
- **F5. Генерация editor-а** — дизайнер генерирует окно плагина 1:1 с canvas
