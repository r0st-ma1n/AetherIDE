# Roadmap AetherIDE

Единый план разработки. Обновлено: 2026-10-07.

## Цель

**Главная идея AetherIDE:** из одного проекта — одного DSP-кода и одного UI из дизайнера —
собирать плагин в нескольких форматах: VST3, CLAP и AU. Код пользователя и фреймворк не
зависят от формата; формат — это тонкий адаптер, который выбирается при сборке.

**v1 — первый настоящий VST3-плагин из AetherIDE.** Пользователь создаёт проект в IDE,
объявляет параметры, пишет DSP в `processBlock`, жмёт Build и получает `.vst3`, который
загружается в DAW, звучит, автоматизируется и сохраняется вместе с проектом DAW.

В v1 у плагина **нет собственного окна**: DAW показывает свой стандартный интерфейс
параметров. Своё окно с виджетами из дизайнера — после v1 (блок F).

### Не входит в v1

- собственный GUI плагина в DAW (блок F);
- MIDI и инструменты, библиотека DSP-примитивов;
- CLAP и AU (блоки G и H), macOS и Linux — v1 собирается и проверяется только на Windows x64;
- live preview, hot-reload, Designer 2.0;
- установщик IDE: v1 — для команды, IDE запускается из репозитория (`make ide-dev`).

При этом архитектура v1 сразу рассчитана на все форматы: ни одна задача v1 не должна
привязывать ядро, GUI или сгенерированный код к VST3 или к Windows.

## Архитектура

```
 Проект в IDE (.aether: метаданные, параметры, UI)
                  │ кодогенерация — не знает про форматы
                  ▼
 Код плагина: Processor + Editor на API Aether
                  │
 framework/core     DSP-контракт, параметры, состояние, шины, PluginInfo
 framework/gui      рендер и ввод виджетов, окно-ребёнок (после v1)
                  │
 framework/formats  адаптеры: vst3 (v1) · clap · au
                  │
 aether_add_plugin(MyPlugin FORMATS VST3 CLAP AU)
```

Правила:

- `core` и `gui` не включают заголовки SDK форматов и не содержат платформенного кода
  вне явно выделенных `platform/`-файлов.
- Адаптер формата — отдельная библиотека в `framework/formats/<format>/` на SDK этого формата
  (VST3 SDK, CLAP API, AU SDK). Адаптер только переводит вызовы хоста в контракт ядра;
  логики плагина в нём нет.
- Окно редактора встраивается через интерфейс адаптера: адаптер отдаёт родительский
  handle (HWND / NSView) и размер, рисует и обрабатывает ввод `gui`.
- Генератор IDE пишет только код на API Aether; список форматов задаётся в CMake.

### Как проект находит фреймворк

Модель как в PyCharm: проект самодостаточен и сам объявляет зависимость с версией,
IDE только настраивает окружение.

- Проект подключает фреймворк через `FetchContent` с закреплённым тегом
  (`GIT_TAG v0.1.0`, `SOURCE_SUBDIR framework`). Без IDE проект собирается сам и берёт
  ровно ту версию, с которой создан.
- IDE при configure передаёт `-DFETCHCONTENT_SOURCE_DIR_AETHER=<фреймворк, с которым запущена IDE>`
  (в v1 — `framework/` репозитория): сеть не нужна, правки фреймворка видны сразу.
- Фреймворк всегда собирается из исходников внутри проекта плагина (как модули JUCE):
  готовых бинарников нет, проблем с ABI (Debug/Release, `/MD`/`/MT`, версии MSVC) тоже.
- Фреймворк экспортирует `AETHER_VERSION`; если версия из IDE ниже нужной проекту —
  понятная ошибка на configure.
- SDK форматов лежат внутри фреймворка, если позволяет лицензия, и не скачиваются
  в каждом проекте.

## Как пользоваться этим документом

- Документ разбит на **блоки** (0, A, B…), блоки — на **задачи** (A1, A2…),
  задачи — на **подзадачи** (чекбоксы).
- Задача берётся в работу целиком: заводится issue, ветка `feat/<issue>-<short-desc>`
  (см. [GIT_CONVENTIONS.md](./GIT_CONVENTIONS.md)).
- PR, который закрывает подзадачи, **в том же PR отмечает их чекбоксы** здесь.
  Задача считается сделанной, когда выполнены все пункты «Готово, когда».
- Размер: **S** — до дня, **M** — 2–4 дня, **L** — неделя и больше.
- Если план меняется — меняем этот документ в отдельном коммите `docs(roadmap): ...`.

## A. Ядро фреймворка

Сейчас `framework/core` — прототип: буфер сам владеет памятью, параметры — простые `float`
без потокобезопасности, нет состояния и нет точки входа плагина. Есть две модели процессора:
`examples/gain` наследует `AudioProcessor` и создаёт параметры отдельно, `PluginProcessor`
хранит их у себя, а `ProcessContext` передаёт ещё одну ссылку. Цель блока — один
контракт, не зависящий от формата, поверх которого пишется любой адаптер (VST3, CLAP, AU),
и headless-хост как первый такой адаптер.

### A0. Уборка · S

- [x] Убрать CLAP из `aether_core`: `FetchContent` тянет его из сети, а код его не использует
      (CLAP вернётся отдельным адаптером в блоке G)
- [x] Удалить `ide/native`: прототип, который IDE не вызывает
- [x] `PluginProcessor.h` не включает виджеты (`Knob`, `Slider`, `Button`) — GUI ядру v1 не нужен

### A1. AudioBuffer без владения памятью · S

Зачем: хост отдаёт готовые указатели на каналы; копировать их в `vector<vector<float>>`
на каждый блок нельзя (аллокации в аудиопотоке).

- [x] `AudioBuffer` хранит `float* const*` + число каналов и сэмплов, ничего не аллоцирует
- [x] Отдельный `OwningAudioBuffer` (или helper) для тестов и offline-рендера
- [x] Раздельные входные и выходные буферы в `ProcessContext` (in-place тоже допустим)
- [x] Обновить `examples/gain` и тесты
- [x] Тестовый счётчик аллокаций (переопределённый `operator new` в тестовом бинарнике):
      тест падает, если `processBlock` аллоцирует

Готово, когда: тест-счётчик подтверждает, что `processBlock` не делает аллокаций; тесты зелёные.

### A2. Параметры, готовые к хосту · M

Зачем: VST3 работает с нормализованными значениями 0..1 и числовыми `ParamID`;
значение пишет один поток, а читает другой.

- [x] Значение хранится в `std::atomic<float>`
- [x] Стабильный 32-битный числовой ID: хеш строкового id в диапазоне, допустимом для всех
      форматов (в VST3 значения со старшим битом зарезервированы), проверка коллизий при `addFloat`
- [x] Строковый id параметра после релиза плагина не меняется — иначе в проектах DAW слетит
      автоматизация; правило записано в документации API
- [x] `toNormalized` / `fromNormalized` с учётом `step` (дискретные параметры)
- [x] Флаги: `automatable`, `isBypass`; единица измерения (`dB`, `%`, `Hz`)
- [x] `valueToText` / `textToValue` для отображения в DAW
- [x] Типы-обёртки: bool (кнопка) и choice (список) поверх float
- [x] `ParameterLayout`: параметры не переаллоцируются после создания (указатели стабильны)

Готово, когда: юнит-тесты на нормализацию, round-trip текста и уникальность ID.

### A3. Сглаживание параметров · S

Зачем: без сглаживания резкий скачок gain даёт щелчки (бывшая задача D1-T1).

- [x] `SmoothedValue` (линейное или экспоненциальное, время задаётся в мс)
- [x] Сброс при `prepareToPlay` с новым sample rate
- [x] Пример использования в GainPlugin

Готово, когда: тест — скачок значения даёт монотонную рампу нужной длины.

### A4. Состояние плагина · S

Зачем: DAW сохраняет и восстанавливает плагин вместе с проектом и пресетами.

- [x] `getState()` / `setState()` в `PluginProcessor`: версия формата + пары `id → value`
- [x] Неизвестные id при загрузке игнорируются, отсутствующие получают default
- [x] Хук для пользовательских данных (opaque blob)

Готово, когда: тест round-trip; загрузка состояния старой версии не падает.

### A5. Контракт плагина и точка входа · M

Зачем: адаптеру любого формата нужно знать, что за плагин, и уметь его создать, не зная класса.

- [x] Одна модель процессора: процессор владеет параметрами, `ProcessContext` несёт
      только буферы и данные блока; `examples/gain` и `PluginProcessor` переведены на неё
- [x] Контракт адаптера описан в `docs/` (какие вызовы, из какого потока, что запрещено
      в аудиопотоке) — общий для VST3, CLAP и AU
- [x] `PluginInfo`: имя, вендор, версия, URL/e-mail, уникальный ID, категория
      (в v1 только Fx; Instrument — вместе с MIDI после v1)
- [x] Конфигурация шин: mono→mono, stereo→stereo (v1 — без sidechain)
- [x] `getLatencySamples()`, `getTailSeconds()`, поддержка bypass
- [x] Макрос `AETHER_PLUGIN(ClassName)` — регистрирует фабрику процессора
- [x] Документация API в Doxygen-комментариях

Готово, когда: адаптер может получить `PluginInfo` и экземпляр процессора, не зная класса.

### A6. Headless-хост и тесты · M

Зачем: проверять плагин без DAW — и руками, и в CI. Headless-хост — первый адаптер:
если он работает только через контракт из A5, ядро действительно не зависит от формата.

- [x] Утилита `aether_host`: грузит плагин, рендерит WAV/синус через `processBlock`
- [x] Заменить `examples/gain/main.cpp` на тест поверх неё
- [x] Тест реального GainPlugin: gain 0.5 → амплитуда 0.5, без щелчков при смене

Готово, когда: `ctest` прогоняет тесты ядра и тест GainPlugin.

## B. Параметры в проекте и кодогенерация

Сейчас генератор создаёт только класс `<Name>UI`, а параметры нигде не объявлены —

- [x] Удаление параметра, к которому привязаны виджеты, — с предупреждением
- [x] Undo/Redo для всех операций (Command Pattern)

### B3. Генерация процессора · L

## F. Собственное окно плагина

Детализируется после выпуска v1. Окно одно для всех форматов, код — в `framework/gui/`.

- **F1. Рендерер** — кроссплатформенный (Windows и macOS), без привязки к формату
- **F2. Отрисовка и ввод виджетов** — Knob/Slider/Button переезжают из `core` в `gui`,
  рисуются и реагируют на мышь
- **F3. Встраивание окна** — интерфейс редактора для адаптеров (родительский handle, размер,
  ресайз, HiDPI); реализация для VST3 (`IPlugView`)
- **F4. Связь UI и хоста** — виджеты меняют параметры через контракт ядра, автоматизация
  двигает виджеты
- **F5. Генерация editor-а** — дизайнер генерирует окно плагина 1:1 с canvas

## G. CLAP-адаптер

встраивание окна из F3.

## H. macOS и AU-адаптер

Детализируется после v1. Сборка фреймворка и IDE на macOS, macOS-job в CI; AUv2-адаптер
