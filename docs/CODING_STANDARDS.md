# Coding Standards

Этот документ фиксирует базовые стандарты разработки для `AetherIDE`. Проект состоит из двух частей:

- `ide/` - desktop IDE на `Electron`
- `framework/` и `ide/native/` - `C++` код на `CMake`

Подробности по отдельным областям вынесены в документы из папки [standards](./standards/).

## Главные принципы

- Любое изменение должно быть понятным следующему разработчику без чтения всей истории PR.
- Архитектурные границы важнее локального удобства.
- Прототип допускает простой код, но не допускает хаотичный код.
- Если правило мешает развитию проекта, его нужно пересмотреть, а не молча игнорировать.

## Структура репозитория

```text
AetherIDE/
├── docs/                  # стандарты, архитектурные заметки, процессы
├── framework/             # core framework и примеры аудио-плагинов
├── ide/                   # Electron IDE, preload, renderer, backend bridge
├── .gitignore
├── CMakeLists.txt
└── README.md
```

## Общие правила по коду

- Новую логику размещать в том модуле, который ей соответствует по ответственности.
- Не смешивать инфраструктурные изменения, рефакторинг и feature-логику в одном большом коммите без причины.
- Имена файлов, сущностей и директорий должны отражать назначение, а не историю появления.
- Предпочитать маленькие функции и небольшие связные классы.
- Комментарии писать только там, где без них теряется смысл или инвариант.
- Не оставлять закомментированный код и временные debug-конструкции в `main`.

## Правила по документации

- При добавлении новой важной подсистемы обновлять `README.md` и документы в `docs/`, если поведение или структура заметно меняются.
- Для нетривиальных архитектурных решений добавлять короткую заметку в `docs/standards/architecture.md` или отдельный ADR позже, если проект дорастет до этого уровня.
- Любая команда запуска, сборки или проверки должна существовать в документации в воспроизводимом виде.

## Правила по зависимостям

- Новую зависимость добавлять только если она решает проблему лучше, чем стандартные возможности текущего стека.
- Для `Electron`-части избегать лишних runtime-зависимостей ради мелких utility-задач.
- Для `C++`-части предпочитать небольшое число прозрачных зависимостей и не размазывать их по нескольким `CMakeLists.txt` без необходимости.

## Quality baseline

- Код должен хотя бы собираться в затронутой части проекта.
- Изменения UI должны быть вручную проверены в `ide`.
- Изменения во `framework` или `ide/native` должны быть проверены сборкой соответствующих target-ов.
- Если тестов ещё нет, в PR всё равно должен быть указан способ ручной проверки.
- Базовые проверки репозитория запускаются через `Prettier`, `ESLint` и `CMake` build pipeline.
