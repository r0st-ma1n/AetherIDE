# Architecture

Границы между модулями AetherIDE.

## Карта модулей

```
AetherIDE/
├── framework/core/         # C++ Aether framework — аудио-абстракции
│   └── examples/gain/      # пример использования API
├── ide/
│   ├── electron/main/      # Electron main process
│   ├── electron/preload/   # IPC bridge
│   ├── native/             # C++ нативный модуль IDE
│   └── src/                # Vue 3 renderer
│       ├── domains/        # фичи по доменам
│       └── shared/         # общий код
└── samples/GainPlugin/     # пример проекта, открываемого в IDE
```

## Границы ответственности

### `framework/core`

- Абстракции аудио-обработки: `AudioProcessor`, `Parameter`, `ProcessContext`
- Переиспользуемый C++ код, независимый от IDE
- Публичный API держится в `include/aether/`

Не должен зависеть от Electron, Node.js или UI-слоя.

### `ide/electron/main`

- Управление жизненным циклом приложения и окна
- Меню, системные диалоги
- Все IPC-handlers (`ipcMain.handle`)
- Доступ к файловой системе

Не должен содержать UI-логику.

### `ide/electron/preload`

- Узкий и явный bridge через `contextBridge`
- Экспортирует только то, что реально нужно renderer

Не должен становиться универсальной оберткой над Node API.

### `ide/src` (renderer)

- Отрисовка интерфейса на Vue 3
- Логика UI Designer, редактора кода, файлового проводника, workspace
- Синхронизация визуального редактора с кодом

Не должен использовать Node API напрямую в обход preload.

### `ide/native`

- C++ нативный модуль, нужный самой IDE
- Интеграция с C++ подсистемой через IPC

Не должен дублировать framework-логику, если она может жить в `framework/core`.

### `samples/GainPlugin`

- Пример проекта, открываемого в IDE
- Содержит `.ui`, `.h`, `.cpp` файлы генерируемые IDE

## Правила роста архитектуры

- Если новый код нужен только IDE — он идёт в `ide/`, не в `framework`
- Если новый код формирует публичный аудио-API — сначала рассматривать `framework/core`
- Повторившуюся логику переносить в общий модуль после второго-третьего реального кейса, не заранее
- `examples/gain` должен оставаться рабочим и читаемым образцом использования API
- Любое новое верхнеуровневое дерево директорий нужно обосновать
- Build-артефакты, кэш и generated-файлы не должны лежать рядом с исходниками
